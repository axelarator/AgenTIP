# Code audit, November 2026

A module-by-module review of cti-graph at commit `276b009`. Each finding gives
the place, what is wrong, and the proposed fix. Severity:

- **high**: loses data, records wrong data, or stalls a scheduled job.
- **medium**: fails silently, or costs the analyst time or context.
- **low**: fragile or misleading, but not currently causing harm.

"Verify" marks a finding that reading alone could not settle; it needs a test.

## Summary

88 findings: 11 high, 36 medium, 41 low. The code is carefully reasoned and
well tested within each module. Most defects sit where modules meet, or where
slow work is done while the database is locked.

The eleven high findings, in the order I would fix them:

| ID | What is wrong | Confirmed by |
|---|---|---|
| H3 | The probe's crawler and downloader follow `file://`, cross-host and redirect URLs taken from an adversary's listing. | Code reading |
| I1 | `analyze_report` / `ingest_report` read any local file and return hex strings from it as "hashes". | Code reading |
| S11 | `query_duckdb` can read and write local files. | A default DuckDB connection read `/etc/hostname`; `enable_external_access=false` blocked it |
| D1 | The dashboard listens on every interface with no login. | Code reading |
| H1 | Closed ports are almost never recorded. | 289 shrinking port sets, 1 `port_closed` row |
| S1 | Probe scans are diffed against the Windows client's view of the same port. | Code reading; 73 change rows follow a win116 scan within 26 hours |
| C1 | Active scans never record their Zeek time window. | 52 active scans, 1 with a window; the imported module does not exist |
| U1 | Hunt rules and FlowCarp models are read from a different folder than the docs name. | `data/hunt_rules/` holds the example; the loader reads `data/clusters/hunt_rules/`, which is empty |
| H2, N2 | Netwatch scans one target at a time, so the hourly run takes about 26 minutes and late results are purged. | `netwatch.log` timings; code reading |
| N1 | Netwatch ingest holds the database lock through the Zeek join and its waits. | Code reading; the "database is busy" banner |

One theme accounts for a third of the medium findings: slow network work done
inside a write connection (N1, G1, F1), reads that open write connections
(S12, T3, G4), and writes that give up instead of retrying when the database is
locked (P1, C2, T2, G3). Together they explain both the "database is busy"
banner and the silently missing history rows.

### Status

Fixed on branch `phase1-fixes` as of 2026-11-13, each with a test that failed
before the change:

- High: S11, I1, D1, C1, S1, N1, U1, and the host side of N2.
- Medium: N3, N4, N5, N7, S6, S12, R2, P1, P2 (reply size and truncation;
  the verdict key waits for the probe batch), C2, C3, C5, T2, T3, G1, G2, G3,
  G4, D2, M1, M2, M3, F1, I2 (list extended, not replaced by the
  public-suffix file).
- Low: N8, N9, N11.

Also fixed, and not in the audit: the test suite set `CTI_DATA_DIR` but
`cti.core` reads it once at import, so a test that did not patch
`core.DATA_DIR` itself wrote into the live cluster store.

Open:

- The probe VM batch, which needs one redeploy: H1, H2, H3, H4 to H7, X1 to X3,
  with S2 and the rest of P2.
- Needs a decision rather than a fix: R1 (API keys sent to the probe), S4 (two
  engines judging the same link), C4 (membership stored twice), N6 (first
  sighting of a port is not a `port_opened`).
- S5, T1, K1 and the remaining low findings.

### What this audit did not cover

- The dashboard front end (`dashboard/ui/`, about 3,000 lines of Svelte) and
  `probe_vm/win116/win_runner.ps1` were not read.
- Tests were surveyed, not read line by line.
- `scripts/`, `setup.sh`, `probe_vm/setup_probe_vm.sh` and `cti-provision` were
  checked for specific risks (destructive flags, how tools are installed, what
  access is granted), not reviewed in full.
- The specialist prompts in `graph/prompts/` were not reviewed.
- Most modules were read with comments and docstrings stripped, so a comment
  that no longer matches its code would mostly have been missed.

### Effect on the plan

Phase 1 of the approved plan listed eleven defects. The audit confirms all of
them and changes three:

- Item 1 (slow netwatch runs) has to be fixed on the probe first (H2); the
  host-side change alone would not help.
- Item 10 (dashboard busy) is N1, and the same fix is needed in G1 and F1.
- Item 9 (control target) stands, and H1 shows change detection for ports needs
  rebuilding at the same time.

It adds the security findings (H3, I1, S11, D1), which should go first, and the
data-correctness findings (H1, S1, C1, U1).

## netwatch (`cti/netwatch/`)

| ID | Sev | Where | Finding | Fix |
|---|---|---|---|---|
| N1 | high | `ingest.py` `ingest` | The Zeek join (`_join_all`) runs inside the read-write DuckDB connection. It makes one OpenSearch query per open port and then sleeps in 10 s steps for up to `CTI_ZEEK_WAIT` (120 s) waiting for late sessions. The writer lock is held throughout, which is why the dashboard shows "database is busy" for minutes each hour, and it breaks the store's own rule that slow work runs with no connection held. | Parse the spool, mark intercepted ports and run the join first; open the connection only for the upsert/diff/selector loop. |
| N2 | high | `jobs.py` `run`, `_collect` | Jobs are submitted and awaited one at a time, so four 40-target jobs take about 26 minutes against an hourly schedule and a 30-minute per-job timeout. On timeout the job is still collected with `purge=True`, so whatever the worker finishes later is deleted unseen. | Submit every job, then poll them together. On timeout collect without purge and leave the job id in a small "outstanding" file that the next run collects first. |
| N3 | medium | `jobs.py` `run` | `queue.drain` removes queued targets before `budget.spend`. A budget refusal, or a failed or rejected submit, drops them for good. | Drain after the budget is granted; re-enqueue the targets of any job that fails to submit. |
| N4 | medium | `watchlist.py` `_candidate_targets`, `build` | `except Exception: return []` and `except Exception: continue`. When the tracking store is locked, every candidate silently drops out of that hour's scan; an unreadable cluster file silently drops the whole cluster. | Catch `TrackingBusy` and `ClusterNotFound`/`JSONDecodeError` specifically, and log a warning with the cluster name. |
| N5 | medium | `ingest.py` `ingest` | One malformed record (no `scan_id` or `target`) raises `KeyError` in `_flatten` part-way through. Rows already written stay, the spool is not purged, and the next run replays it. Undecodable lines are skipped without a count. | Validate records while reading the spool, count and log rejects, and move a file that cannot be ingested to `spool/bad/` so it cannot block later runs. Verify that replaying a spool file does not duplicate `service_changes`. |
| N6 | medium | `ingest.py` `_diff` | A port with no earlier snapshot has `base is None`, so no `port_opened` is recorded. Verify whether a port first found by the full-tier sweep on an already-tracked host is reported at all. | If the host has earlier scans that covered the port's profile, treat a first open snapshot as `port_opened`. |
| N7 | medium | `ingest.py` `intercepted_ports` | The only guard against a contaminated probe path is a fixed port list (default `53`). The fake 443/8080 answers of 2026-11-06 to 11-11 passed straight through. | Add a control target with known ports to every run; if it reports anything else, set the run's spool aside and log an error instead of ingesting (plan item 9). |
| N8 | low | `ingest.py` `_diff` | The `old_hits` expression mixes `and` and a conditional in one line and is correct only by accident of precedence. | Rewrite as two plain statements. |
| N9 | low | `queue.py` `drain` | A queue file that fails to parse is deleted. | Rename it to `*.bad` and keep it. |
| N10 | low | `candidates/neighbourhood.py`, crontab | The `sweep` tier is only filled by `--discover` and only scanned by a run whose `--tiers` includes `sweep`. Neither is in the crontab, so the neighbourhood sweep the README describes as weekly never runs. | Either add the weekly cron line or say in the README that it is manual. |
| N11 | low | `candidates/ct.py` `stream` | Uses `asyncio.get_event_loop()` inside a coroutine, which is deprecated. | Use `asyncio.get_running_loop()`. |

Replaying a spool file does not duplicate changes: `record_service_change` is
`ON CONFLICT ... DO NOTHING` on (scan, target, port, field), and snapshots are
upserts. N5 is therefore about the blocked spool, not duplicates.
